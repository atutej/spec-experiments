# DSpark drafter, TARGETGEN for the Nemotron-Terminal-fine-tuned Qwen3-0.6B

The missing control of the target-by-drafter comparison. The target is Qwen3-0.6B fine-tuned on the Nemotron-Terminal corpus
(`pipelines/sft/experiments/sft_qwen3_0_6b_nemotron-terminal-corpus`, public at
https://huggingface.co/atutej/sft_qwen3_0_6b_nemotron-terminal-corpus-20261011, commit `cd76e0562da3c278e2e031b961fd7cd260d12d6d`). Here the
responses to the 100k conversations are **regenerated by that model** (turn by turn, thinking on, temperature 0.6 / top-p 0.95 / top-k 20, as the base
targetgen experiment), and the drafter is trained on its hidden states. Siblings:

|  | data | target | rollout acceptance length (on the target's own rollouts) |
|---|---|---|---|
| `..._nemotron-terminal-corpus_targetgen` | the base model's regenerated responses | base Qwen3-0.6B | 4.058 |
| `..._nemotron-terminal-corpus_itw` | corpus completions (DeepSeek-V3.2) | base Qwen3-0.6B | 3.430 (3.736 on the SFT model's rollouts) |
| `..._sft-..._itw` | corpus completions | SFT model | 4.575 |
| **this experiment** | the SFT model's regenerated responses | SFT model | to be measured |

The question: after SFT, how much of the itw gap remains? Compare this drafter with the SFT-target itw drafter (4.575) on the same
prompts and target; the base-model pair (4.058 vs 3.430) is the reference for the size of the gap.

## Run

```
bash vista/submit_chain.sh [--dry-run]    # login node: (the sample is linked there), regen, regen (retry), prepare+train; all on gb in the CGAI-gb reservation
bash vista/run.sh [export] [regen] [prepare] [train]   # as-is on an idev node (regen and train need 4 GPUs)
bash vista/submit_eval.sh [CHECKPOINT_NAME]            # rollout acceptance eval, target = the SFT model (../../tools/eval_acceptance/)
```

- `export` links the base targetgen experiment's 100k sample (same conversations everywhere), else exports it.
- `regen` serves the SFT model (bf16) on 4 GPUs and runs `speculators regenerate-responses --resume`. The base model took 2h55m on one gb node; this model
  writes much longer answers (about 2.6x for later turns in the rollout eval), so it may need more than one 12 h job: the chain therefore has TWO regen
  jobs (the second starts after the first even if it timed out, and resumes; if the first finishes, the second exits quickly). Three gb jobs is all the QOS
  allows at once: do not queue other gb jobs (evals) before the chain ends. MAX_GEN_TOKENS stays 8192, so more conversations than with the base model are cut short
  (28% of first-turn rollouts hit 8192): fewer rows per conversation, a property of this target. Check the truncated count in the regen log.
- `prepare` and `train` run in ONE gb job (`prepare,train`: the gb QOS allows only 3 submitted jobs, and every job is on gb in the reservation, CPU stages included), as in the base
  targetgen experiment (train about 3 h there); the trainer uses 16384 / 6144 anchors.
- At the end of training the drafter is uploaded to the Hub (public, `<this folder>-<date>`, best and latest checkpoint) when `HF_REPO` is set (default `auto` for full runs).
- W&B: project `marin_speculator`, run name = this folder's name.

## Status (2026-10-12)

Folder created from the base targetgen experiment (settings, `vista/` only; no genai launcher, no tuning scripts). Smoke test through `run.sh export regen
prepare train` on a gb node (`REGEN_LIMIT=300 MAX_STEPS=10`): the SFT model was downloaded from the Hub and served in bf16, regenerated all 300 conversations into 1,203 rows
with 0 failures, prepare and 10 training steps ran, the validation epoch ran and `checkpoint_best` was written. The smoke test caught one bug, fixed: `export` linked the
shared sample into a `source/` folder that did not exist yet.

`submit_chain.sh`: the export step (a symlink to the base targetgen experiment's sample) is done on the login node at submission, not as a gg job; if that sample is missing the
export stage stays in the chain. The second `regen` is a conditional retry (`afternotok` + `--kill-on-invalid-dep=yes`: it starts only if the first regen failed or timed out, Slurm
removes it otherwise); `prepare` waits for either regen (`afterok:a?afterok:b`). Only dry-run tested: the first real submission is the real test, check `squeue` right after it
(the retry should be pending on a dependency). Not done: the full run.
